# Capture environments — F1 v0.4 development

## Orthogonal settings

- `ENABLE_F1_V04_DEVELOPMENT=true` permits executing the *candidate*, not-yet-approved v0.4 scientific study and its development helpers. It **does not** turn capture off.
- `REQUIRE_ACTIVE_CAPTURE=true` rejects any new `/join` without a fresh Windows host-recorder heartbeat, required running media streams, and an unused capture-run UUID.
- `REQUIRED_CAPTURE_STREAMS=screen_and_webcam` requires both streams at admission. An explicit `screen` policy exists for screen-only development tests, but **not** for webcam-required runs.
- `ACTIVE_CAPTURE_MAX_AGE_SECONDS=15` is the maximum permitted *heartbeat age*, not the maximum recording duration. A running recorder refreshes its marker every two seconds.

These settings control separate concerns: candidate study access, development-only helpers, and recording *admission policy*. Do not mistake recorded development for an approved research deployment.

## Mode 1: ordinary development (no camera required)

From the repo root on Windows:

```powershell
# To override any REQUIRE_ACTIVE_CAPTURE=true in .env for this PowerShell session:
$env:REQUIRE_ACTIVE_CAPTURE = "false"
docker compose up -d --build --wait
```

The normal app works without the Windows recorder. Existing browser UI/keyboard/rrweb telemetry remains independent of webcam capture.

## Mode 2: recorded development (webcam AND screen required)

```powershell
# Remove any temporary shell override; the recorded-dev Compose override is authoritative.
Remove-Item Env:REQUIRE_ACTIVE_CAPTURE -ErrorAction SilentlyContinue
# Terminal A: run the host recorder, wait for "Recording ready."
python tools/windows_capture/record.py preflight
python tools/windows_capture/record.py record
```

In a second PowerShell terminal:

```powershell
docker compose -f compose.yaml -f compose.recorded-dev.yaml up -d --build --wait
docker compose -f compose.yaml -f compose.recorded-dev.yaml exec app python -c "from solo_harness.config import get_settings; s=get_settings(); print('development=', s.enable_f1_v04_development, 'capture_required=', s.require_active_capture, 'streams=', s.required_capture_streams, 'heartbeat_max_age=', s.active_capture_max_age_seconds)"
```

Open `http://127.0.0.1:8000/join`. With no recorder, admission fails (403). Once the independent Windows recorder is ready, admission succeeds and `sessions.capture_run_id` links the session to `research-data/capture-runs/<run-id>/`.

Stop media after the session using Ctrl+C in Terminal A. Use **a fresh recording run and participant ID for each new study session**: one capture-run UUID can be linked to one session only.

For a screen-only development experiment, set `REQUIRED_CAPTURE_STREAMS=screen` explicitly in the standard environment and use `record --no-webcam`. The recorded-dev override deliberately rejects that mode.

## Critical behavior boundaries

1. The server validates recorder readiness only when creating the session. The heartbeat helps reject stopped or crashed recorders **at enrollment**; it does not currently pause an ongoing session if the camera later disconnects. For actual collection, monitor stream continuity and mark/intervene on recording gaps; do not assume guaranteed continuous capture.
2. The recorder validates real frame progress before publishing its marker, and refreshes it only while both selected FFmpeg processes are alive and continuing to report progress. Unexpected stream loss is recorded as an `INTERRUPTED` manifest instead of a normal completion. The marker must match the manifest's `RECORDING` status and each required stream's `RUNNING` status.
3. `REQUIRE_ACTIVE_CAPTURE=true` does not require the participant browser to grant camera permission: capture happens on the **Windows host**, not through browser `getUserMedia`. Browser telemetry (rrweb, keyboard, semantic events) is a separate component.
4. This patch changes no LLM, SOLO, Paas, assessment or Judge behavior, and adds no database migration.
5. Do not collect participant webcam/screen data until explicit consent, recording notices, privacy/retention safeguards, and study approval are in place. Screen capture can contain unrelated sensitive information.
6. Running Docker in capture-required mode alone **does not start the recorder**. Always start `record.py` separately on the Windows desktop used by the participant.

## Troubleshooting

- If `/join` reports "study not ready", inspect the app logs for `Capture-required enrollment blocked: ...`.
- `missing_recorder_heartbeat` means an older recorder is still running, or marker was generated by an older version. Restart `record.py` with the updated file.
- `required_stream_not_running` can mean `record --no-webcam` was used while both streams were required.
- `stale_recorder_heartbeat` usually means the recorder stopped/crashed, the bind mount isn't shared, or clocks diverged; verify the host-recorder terminal and `research-data/active_capture.json`.
- `capture run already assigned` means the same recording was already used for another session. Start a new recorder run.
- If activation is blocked for a duplicate institutional ID, the response can be the same 403; use a fresh test identity, not an existing study participant's ID.
